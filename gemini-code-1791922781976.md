# Especificación maestra de requisitos — Inventario AudacIA

**Versión:** 1.1 consolidada y cerrada  
**Uso:** documento de referencia para una IA desarrolladora o un equipo de desarrollo de 4 integrantes  
**Empresa:** AudacIA, Barranquilla, Colombia[cite: 1]  
**Tipo de proyecto:** sistema local de inventario, sin ventas ni compras comerciales[cite: 1]

## Cómo utilizar este documento

Este documento consolida las decisiones expresadas por el solicitante y corrige contradicciones de borradores anteriores[cite: 1]. La IA desarrolladora debe tratar las reglas funcionales como requisitos obligatorios e innegociables[cite: 1]. Las recomendaciones técnicas se identifican como recomendaciones[cite: 1]. Los puntos configurables aparecen en la sección **Decisiones pendientes y tratamiento provisional**: no deben resolverse inventando requisitos[cite: 1].

La implementación debe hacerse por módulos, con pruebas en cada etapa[cite: 1]. No se debe reescribir Haku ni generar toda la aplicación de una sola vez[cite: 1].

## 1. Resumen ejecutivo

Inventario AudacIA será una aplicación web local desarrollada principalmente en Python[cite: 1]. Se usará desde navegadores de computadores, teléfonos y tabletas conectados a la red local por Wi-Fi o Ethernet[cite: 1]. Los equipos clientes no instalarán Python, el modelo de IA ni una aplicación propia[cite: 1].

El sistema permitirá registrar productos, categorías, almacenes, ubicaciones físicas, existencias, entradas, salidas, préstamos (con devoluciones totales, parciales o bajas por daño), traslados y ajustes por conteo físico[cite: 1]. También ofrecerá búsqueda, informes, alertas de stock bajo y consultas y operaciones por voz mediante **Haku Inventario**[cite: 1].

El inventario se utiliza exclusivamente para control físico y trazabilidad de AudacIA[cite: 1]. No incluirá ventas, compras comerciales, proveedores, facturación, precios ni cálculo de valor económico[cite: 1].

### Capacidad prevista

- Hasta aproximadamente 1.000 productos en la primera etapa[cite: 1].
- Menos de 10 usuarios simultáneos; uso habitual aproximado de 2[cite: 1].
- Cantidad variable de almacenes y ubicaciones[cite: 1].
- Tres roles: superusuario, administrador y usuario[cite: 1].
- Todo debe ser gratuito, local y sin dependencia operativa de servicios en la nube[cite: 1].

- Usuarios normales asignados a un único almacén, con permiso para crear/editar datos maestros y movimientos dentro de su almacén[cite: 1].

- Productos con código interno automático inmutable y código de barras opcional[cite: 1].

- Historial de cambios, auditoría inmutable, reportes, gráficos y copias de seguridad[cite: 1].

## 3. Contexto existente de Haku

El README entregado describe Haku como una aplicación conversacional local en Python, con Llama 3.1 8B, ChromaDB, reconocimiento de voz mediante faster-whisper, síntesis mediante Piper y módulos separados de conversación, memoria, interfaz y voz[cite: 1]. La configuración documentada utiliza Python 3.11 y una GPU NVIDIA para una respuesta de voz práctica[cite: 1]. El acceso al modelo actual se serializa mediante un bloqueo porque el modelo no es reentrante[cite: 1].

Antes de integrar, la IA desarrolladora debe inspeccionar el repositorio real, confirmar las versiones instaladas y ejecutar las pruebas existentes[cite: 1]. El README no debe tratarse como sustituto del código[cite: 1].

### Reglas para proteger Haku existente

1. No reescribir Haku desde cero[cite: 1].
2. No romper el modo Visitante ni cambiar su personalidad o comportamiento de exposición sin necesidad demostrada[cite: 1].
3. Mantener separadas la conversación pública y las operaciones privadas del inventario[cite: 1].
4. Evitar conflictos de dependencias[cite: 1]. Se permite un entorno virtual independiente para Inventario AudacIA, manteniendo Haku en su entorno compatible[cite: 1].
5. No duplicar el modelo de lenguaje en memoria por defecto[cite: 1]. Primero se debe medir el comportamiento cuando ambos usos están activos[cite: 1].
6. No almacenar inventario en la memoria conversacional, el corpus RAG ni el prompt del modelo[cite: 1]. La fuente de verdad será la base de datos[cite: 1].

## 4. Arquitectura y despliegue

### 4.1 Servidor

Un computador Windows de la empresa ejecutará la aplicación web, la base de datos, el adaptador de Haku y los servicios necesarios[cite: 1]. Debe permanecer encendido durante la jornada laboral e iniciar automáticamente los servicios al arrancar[cite: 1].

Hardware temporal previsto para desarrollo/pruebas: NVIDIA RTX 5070 Ti con 16 GB de VRAM, 32 GB de RAM y procesador aproximadamente equivalente a Intel Core Ultra 9 275HX[cite: 1]. No se debe codificar la aplicación para depender de un modelo concreto de CPU ni de la GPU para operaciones ordinarias de inventario[cite: 1]. La GPU se reserva principalmente para IA y voz[cite: 1].

### 4.2 Dispositivos cliente

El cliente solo necesita navegador y acceso a la red local[cite: 1]. Puede ser un computador, teléfono o tableta[cite: 1]. El micrófono, los altavoces de respuesta y la cámara serán los del dispositivo cliente cuando el usuario los habilite en el navegador[cite: 1].

### 4.3 Red local

- Acceso por Wi-Fi o Ethernet dentro de la red local autorizada[cite: 1].
- No publicar la aplicación en Internet ni configurar redirecciones de puertos desde el router[cite: 1].
- Recomendable asignar una IP local fija o una reserva DHCP[cite: 1].
- Configurar el cortafuegos de Windows para limitar el acceso al puerto de la aplicación a la red local necesaria[cite: 1].
- Si se pierde Internet pero la red local sigue operativa, el sistema debe continuar funcionando[cite: 1]. Las consultas externas opcionales de códigos de barras no pueden ser necesarias para registrar productos[cite: 1].
- Si se cae la red local, los equipos cliente pierden acceso; el servidor puede seguir funcionando localmente desde sí mismo[cite: 1].

### 4.4 Micrófono y cámara: requisito de HTTPS

Los navegadores modernos requieren un contexto seguro para la captura de micrófono y cámara[cite: 1]. `http://localhost` suele ser aceptado en el propio dispositivo, pero acceder desde otro dispositivo por una IP LAN mediante HTTP normalmente no es suficiente[cite: 1]. Por ello, publicar solo `http://192.168.x.x` no satisface de forma fiable el requisito de voz y escaneo móvil[cite: 1].

Requisito: implementar HTTPS dentro de la red local sin pagos recurrentes[cite: 1]. La solución recomendada es un certificado emitido por una autoridad certificadora local confiable (ej. `mkcert`) para los dispositivos que utilizarán el sistema[cite: 1]. Puede ser necesario un paso único de instalación de confianza del certificado en cada dispositivo; esto no implica instalar una aplicación, pero sí configurar el dispositivo[cite: 1]. Se documentará paso a paso y se probará en los navegadores objetivo[cite: 1]. No se debe deshabilitar la seguridad del navegador como solución normal[cite: 1].

## 5. Stack técnico recomendado

- Python 3.11 para mantener compatibilidad con el entorno descrito para Haku, salvo que la inspección del repositorio indique una incompatibilidad concreta[cite: 1].

- PostgreSQL como base de datos local para manejar transacciones y operaciones concurrentes con integridad[cite: 1].
- HTML, CSS y JavaScript para la interfaz adaptable; no es obligatorio introducir un framework frontend pesado[cite: 1].
- API interna autenticada para que Haku invoque acciones de la aplicación[cite: 1].
- Pruebas automatizadas compatibles con Django, más pruebas de integración y de voz[cite: 1].
- Scripts Python y herramientas PostgreSQL para copias y restauración[cite: 1].

Todas las dependencias deben ser gratuitas[cite: 1]. Las versiones deberán fijarse en archivos de requisitos y validarse con pruebas[cite: 1]. Las operaciones de inventario seguirán funcionando cuando Haku no esté disponible[cite: 1].

## 6. Usuarios, roles y permisos

### 6.1 Datos de cuenta

Datos mínimos obligatorios: nombre completo, nombre de usuario y contraseña[cite: 1]. No se requieren correo, teléfono, documento de identidad ni otros datos personales[cite: 1]. Se guardarán únicamente los datos necesarios para identificar cuentas y atribuir operaciones[cite: 1].

### 6.2 Roles y alcance exacto de permisos

**Superusuario**
- Único en el sistema[cite: 1].
- Puede administrar todo el sistema, todos los almacenes, usuarios, administradores, configuración, auditoría y copias de seguridad.
- No puede eliminarse mediante la aplicación ni perder sus permisos.
- **Recuperación de acceso:** como no existen correos ni teléfonos, debe implementarse un comando administrativo local por consola (CLI) en el servidor Windows (ej. `python manage.py recuperar_superusuario`) que permita restablecer su contraseña y desbloquear la cuenta únicamente a quien tenga acceso directo al servidor, dejando registro en la auditoría[cite: 1].

**Administrador**
- Acceso a todos los almacenes y a todas las funciones operativas y maestras de inventario[cite: 1].
- Puede crear, modificar, activar, desactivar y eliminar lógicamente usuarios normales[cite: 1].
- Puede confirmar ajustes de conteo físico, archivar/eliminar lógicamente registros maestros, fusionar productos duplicados y autorizar excepciones de productos fuera del almacén principal de su categoría[cite: 1].
- No puede crear un segundo superusuario ni modificar al superusuario[cite: 1].
- Provisionalmente (por principio de menor privilegio), solo el superusuario puede crear, modificar o desactivar cuentas de otros administradores[cite: 1].

**Usuario**
- Tiene asignado obligatoriamente un único almacén[cite: 1].
- **Permisos sobre datos maestros en su almacén:** SÍ puede crear y editar productos, ubicaciones y categorías vinculadas a su almacén asignado[cite: 1].
- **Permisos sobre movimientos en su almacén:** SÍ puede registrar entradas, salidas, préstamos, devoluciones (totales, parciales o bajas por daño), reversiones/movimientos compensatorios de su almacén y registrar conteos físicos preliminares[cite: 1].
- **Permisos sobre traslados hacia otros almacenes:** SÍ puede iniciar y registrar un traslado de productos desde su almacén asignado hacia otro almacén destino[cite: 1]. Para ello, el sistema le permitirá ver únicamente la lista de nombres de almacenes activos como destino elegible, pero **nunca** podrá ver el stock, las ubicaciones ni el historial del almacén destino (ni antes ni después de confirmar el traslado)[cite: 1].
- **Restricciones del rol Usuario:** NO puede confirmar el ajuste final de un conteo físico (requiere confirmación de un Administrador o Superusuario)[cite: 1], NO puede archivar ni eliminar lógicamente productos/ubicaciones/categorías/almacenes[cite: 1], NO puede fusionar productos duplicados, NO puede administrar cuentas ni configuración global[cite: 1], y NO puede consultar, buscar ni solicitar por Haku información de almacenes a los que no tiene acceso[cite: 1].

### 6.3 Estados de cuentas

Las cuentas podrán activarse, desactivarse y eliminarse lógicamente[cite: 1]. Desactivar una cuenta impide su acceso de inmediato en la siguiente petición HTTP o interacción de voz, invalidando su sesión activa y cerrando cualquier contexto de Haku[cite: 1]. Los registros históricos se conservan[cite: 1].

### 6.4 Contraseñas y sesiones

- Nombre de usuario y contraseña individual[cite: 1].
- Mínimo confirmado: 7 caracteres, con al menos una letra y un número[cite: 1].
- No guardar contraseñas en texto plano; utilizar el mecanismo de hashing seguro de Django (PBKDF2/Argon2)[cite: 1].
- Bloquear temporalmente nuevos intentos después de 5 intentos fallidos[cite: 1]. La duración del bloqueo debe definirse en variables de configuración (ej. 15 minutos por defecto, configurable en `.env`)[cite: 1].
- Opción “Recordar este dispositivo durante 7 días” implementada con sesiones seguras, revocables y con caducidad real en el servidor[cite: 1]. Si no se marca, la sesión caduca al cerrar el navegador o tras inactividad estándar[cite: 1].
- Se permite iniciar sesión desde varios dispositivos[cite: 1].
- Los usuarios podrán cambiar su propia contraseña ingresando su contraseña actual.
- No se registrarán todos los accesos normales ni consultas ordinarias en la auditoría de negocio del inventario[cite: 1].

## 7. Almacenes, ubicaciones y categorías

### 7.1 Almacenes

La cantidad es variable: se podrá crear, renombrar, activar, desactivar o eliminar lógicamente siguiendo las reglas de traslado[cite: 1]. Campos: nombre obligatorio, descripción opcional y estado (activo/inactivo).

Un almacén con productos/existencias no puede desactivarse ni eliminarse directamente[cite: 1]. Antes de hacerlo, el sistema debe obligar a seleccionar un almacén destino y trasladar todos los productos/stock, o distribuirlos según selección, ofreciendo siempre la opción de cancelar[cite: 1].

### 7.2 Ubicaciones

Sección y estantería son el mismo concepto; existe un único nivel de ubicación perteneciente a un almacén[cite: 1]. Su nombre es libre (“A”, “B-03”, “Estante rojo”, “Zona cables”, etc.) y la descripción es opcional[cite: 1].

Un producto puede figurar en varias ubicaciones dentro de un mismo almacén[cite: 1]. **No se gestionará cantidad por ubicación:** el sistema controlará el stock numérico del producto por almacén y mantendrá la lista de ubicaciones donde se encuentra dentro de ese almacén[cite: 1]. Nunca se deben mostrar ni inventar cantidades numéricas por estantería[cite: 1].

Si se renombra una ubicación, se debe conservar el historial del nombre anterior en auditoría[cite: 1]. Si se desea desactivar o eliminar una ubicación que tiene productos asociados, el sistema debe exigir trasladar primero esos productos a otra ubicación del mismo almacén (permitiendo cancelar) hasta dejarla vacía[cite: 1].

### 7.3 Categorías

Categorías simples, sin subcategorías ni árboles jerárquicos. Campos: nombre obligatorio, almacén principal obligatorio y estado.

Los productos de una categoría pertenecen por defecto al almacén principal asignado a dicha categoría[cite: 1]. Si un usuario autorizado cambia el almacén principal de una categoría, el sistema debe exigir dentro de la misma operación el traslado de todos sus productos y existencias al nuevo almacén (o su distribución controlada), con opción de cancelar[cite: 1].

Se permiten excepciones poco frecuentes en las que un producto tenga existencias en un almacén distinto al de su categoría (por ejemplo, tras un traslado entre almacenes)[cite: 1]. Cuando se cree o asigne manualmente una excepción de categoría-almacén, debe requerir confirmación explícita y registrar la justificación en auditoría[cite: 1].

## 8. Productos y existencias

### 8.1 Datos y reglas de código interno

Cada producto tendrá, como mínimo:
- Identificador interno de base de datos[cite: 1].
- **Código interno único generado automáticamente:** tendrá formato legible con las 3 primeras letras de la categoría inicial en mayúsculas seguidas de un consecutivo de 4 dígitos (ej. `CAB-0001`, `HER-0001`, `BAT-0001`). **Regla de inmutabilidad:** una vez creado el producto, su código interno es **estrictamente inmutable** para siempre, incluso si el producto cambia posteriormente de categoría, de nombre o de almacén.
- Nombre obligatorio[cite: 1].
- Código de barras opcional y único[cite: 1].
- Categoría obligatoria.
- Stock inicial histórico (registrado al crear el producto, inmutable; genera automáticamente el movimiento inicial de creación)[cite: 1].
- **Stock disponible actual por almacén** (unidades físicamente disponibles en el almacén)[cite: 1].
- **Stock actualmente en préstamo por almacén** (unidades entregadas en préstamo pendientes de devolución).
- Stock mínimo configurable por producto[cite: 1].
- Lista de una o varias ubicaciones dentro del almacén donde se encuentre[cite: 1].
- Equivalencia opcional de empaque/paquete (ej. 1 paquete = N unidades base, opcional)[cite: 1].
- Estado: activo o archivado/inactivo.
- Descripción opcional[cite: 1].

### 8.2 Código de barras

El código de barras es adicional al código interno; un producto puede no tenerlo o tener como máximo uno[cite: 1]. Al escanear (con cámara del navegador o lector USB tipo teclado) un código registrado, el sistema abre la ficha existente y ofrece consultar, modificar o registrar entrada/salida. Nunca crea un duplicado automático[cite: 1]. Si el código no existe, informa y ofrece ir al formulario de creación precargando el código escaneado[cite: 1].

### 8.3 Duplicados y fusión

- Código interno: único siempre[cite: 1].
- Código de barras: único cuando no sea nulo/vacío[cite: 1].
- Nombres parecidos: al escribir o dictar un nombre similar a otro existente, el sistema muestra una advertencia con las coincidencias antes de guardar, permitiendo cancelar o confirmar que es un artículo distinto.
- Existirá una función administrativa (solo Administradores y Superusuario) para **fusionar dos productos duplicados**, trasladando el stock y reasignando el historial de movimientos al producto principal, dejando el duplicado archivado y auditado[cite: 1].

### 8.4 Stock mínimo y alertas

Reglas matemáticas estrictas:
- **Stock bajo:** `stock_disponible_actual < stock_minimo` (y mayor que 0)[cite: 1].
- **Sin stock (agotado):** `stock_disponible_actual == 0`[cite: 1].

Las alertas se muestran en la web y mediante Haku con mensajes informativos internos (nunca sugerencias comerciales de compra)[cite: 1].

### 8.5 Conversión opcional de paquetes

El stock siempre se almacena y contabiliza en **unidades base enteras**[cite: 1]. Opcionalmente, en un producto se puede definir un factor de empaque (ej. `nombre_empaque = "Paquete"`, `unidades_por_empaque = 12`) para que al registrar una entrada el usuario pueda elegir ingresar "2 paquetes" y el sistema sume automáticamente `24` unidades base al stock, dejando constancia en la observación del movimiento[cite: 1].

### 8.6 Archivar y eliminar

Solo Administradores y el Superusuario pueden archivar o eliminar lógicamente un producto[cite: 1]. Nunca se borran físicamente productos que tengan movimientos o auditoría[cite: 1]. Los productos archivados se ocultan de las listas operativas predeterminadas pero conservan todo su historial consultable mediante filtro[cite: 1].

## 9. Movimientos de inventario

Todo cambio de existencias debe ocurrir mediante un registro de movimiento dentro de una transacción atómica de base de datos (`transaction.atomic()` y bloqueo de fila `select_for_update()`)[cite: 1].

### 9.1 Campos comunes

Identificador único, clave de idempotencia (para evitar duplicados por doble clic o reintento de red/voz), tipo de movimiento, producto, cantidad en unidades base, almacén origen/afectado, almacén destino (en traslados), ubicación afectada, usuario autenticado que registra, fecha y hora en zona horaria `America/Bogota` (Barranquilla), motivo/observación, destinatario en texto libre (en salidas y préstamos), stock disponible anterior y posterior, estado del movimiento y referencia al movimiento original (en devoluciones, bajas de préstamo o reversiones).

### 9.2 Entrada

Aumenta el stock disponible del producto en el almacén/ubicación indicada[cite: 1, 4]. Solo se registra mercancía físicamente recibida[cite: 1].

### 9.3 Salida

Descuenta del stock disponible[cite: 1, 4]. Requiere: producto, cantidad, ubicación origen, **motivo obligatorio** y **destinatario en texto libre** (persona que recibe, sin obligar a que tenga cuenta en el sistema)[cite: 1, 4]. La observación adicional es opcional y el sistema puede autogenerar un texto base editable (ej. *"María registró la salida de 5 cables HDMI desde la ubicación B para Carlos"*)[cite: 1, 4]. No se permite stock negativo bajo ninguna circunstancia[cite: 1].

### 9.4 Préstamos, devoluciones parciales y bajas por daño

- **Préstamo:** descuenta la cantidad del `stock_disponible` y la suma al `stock_en_prestamo` del almacén. Exige indicar el **destinatario en texto libre** (persona responsable que recibe el artículo) y registra fecha/hora y ubicación origen[cite: 1, 4]. Cada préstamo mantiene un saldo de `cantidad_pendiente_devolucion` y un estado (`ABIERTO`, `DEVUELTO_PARCIAL`, `CERRADO`).
- **Devolución (total o parcial):** se vincula al préstamo activo[cite: 1]. El usuario indica cuántas unidades se están devolviendo (puede ser menor o igual a la `cantidad_pendiente_devolucion`). Esa cantidad se suma de vuelta al `stock_disponible` del almacén y se resta de la cantidad pendiente del préstamo. Si la cantidad pendiente llega a `0`, el préstamo pasa a `CERRADO`; si aún quedan unidades prestadas, queda en `DEVUELTO_PARCIAL`.
- **Cierre/Baja de préstamo por daño o pérdida:** si un artículo prestado se daña o pierde y no puede volver al inventario usable, el usuario puede registrar una baja sobre el préstamo indicando la cantidad dañada/perdida y el motivo. Esto reduce la `cantidad_pendiente_devolucion` del préstamo (cerrándolo si llega a 0) y registra el incidente en el historial y auditoría, pero **NO suma esas unidades al `stock_disponible`**.

### 9.5 Traslados

- **Traslado interno (mismo almacén):** actualiza las ubicaciones registradas del producto en ese almacén sin alterar el stock total[cite: 1].
- **Traslado entre almacenes:** descuenta la cantidad del almacén origen y la suma al almacén destino dentro de una única transacción atómica[cite: 1]. Un Usuario normal puede enviar productos desde su almacén hacia otro almacén seleccionando el nombre del almacén destino, aunque no tenga permisos para visualizar el inventario del almacén receptor[cite: 1].
- **Traslados masivos:** disponibles para vaciar una ubicación o almacén antes de inactivarlo, o al cambiar el almacén principal de una categoría[cite: 1].

### 9.6 Correcciones y reversiones

Los movimientos confirmados son inmutables y nunca se eliminan con `DELETE`[cite: 1]. Para corregir un error se registra una **reversión** o **movimiento compensatorio** vinculado al ID del movimiento original, exigiendo el motivo, ajustando el stock en sentido inverso (siempre que no provoque stock negativo) y marcando el movimiento original como `REVERTIDO` en la trazabilidad[cite: 1, 4].

### 9.7 Conteo físico

Cualquier usuario con acceso al almacén puede introducir la cantidad física contada para un producto, y el sistema calcula la diferencia (`contado - stock_sistema`)[cite: 1, 4]. Sin embargo, **solo un Administrador o el Superusuario puede confirmar y aplicar el ajuste**, lo cual genera el movimiento de tipo `Ajuste por conteo físico` con el stock anterior, el nuevo stock, la diferencia, el motivo, el usuario y la fecha[cite: 1, 4].

## 10. Auditoría e historial

La tabla de auditoría es obligatoria e inmutable desde la aplicación web (incluso para el superusuario: sin botones ni endpoints de edición o borrado)[cite: 1].

### 10.1 Eventos auditados y datos

Se audita toda creación, edición, cambio de estado, archivado, fusión, traslado, movimiento de inventario, cambio de permisos/cuentas, recuperación de superusuario, copia de seguridad y acción ejecutada vía Haku que modifique datos[cite: 1]. Guarda: fecha/hora local, usuario, acción, tipo de entidad, ID afectado, instantánea JSON de valores anteriores y nuevos, motivo y resultado[cite: 1, 4].

No se registran en la auditoría de inventario las búsquedas ni consultas de solo lectura ordinarias[cite: 1].

## 11. Reportes e interfaz

- **Identidad y pronunciación:** el sistema se muestra como **Inventario AudacIA** (con "IA" en mayúsculas en texto)[cite: 1, 4], pero en síntesis de voz (Piper) debe normalizarse fonéticamente como **"Audacia"** para que nunca pronuncie "AudakIA"[cite: 1].
- **Dashboard:** total de productos, alertas de stock bajo (`< minimo`), alertas sin stock (`== 0`), préstamos activos y últimos movimientos del ámbito autorizado[cite: 1, 4].
- **Ficha de producto:** muestra código interno inmutable, código de barras, nombre, categoría, almacén, ubicaciones registradas, `Stock inicial`, **`Stock disponible en almacén`**, **`Cantidad actualmente en préstamo`**, `Stock mínimo`, estado e historial[cite: 1].
- **Informes y gráficos:** existencias actuales, bajo stock/sin stock, movimientos filtrables (fecha, producto, usuario, almacén, tipo), préstamos abiertos/parciales con nombre del responsable y fecha, productos sin movimiento en N días, y gráficos simples de productos por categoría y entradas vs. salidas[cite: 1, 4].

## 12. Haku Inventario y Haku Visitante

### 12.1 Separación funcional y de salida de audio

- **Haku Visitante:** corre en el servidor para atención pública[cite: 1]. Usa el micrófono y los altavoces físicos del servidor y **no tiene acceso** a la base de datos ni a la API de inventario[cite: 1].
- **Haku Inventario:** se utiliza desde el navegador de los dispositivos clientes[cite: 1].
  - **Activación del micrófono (Push-to-Talk):** en computadores se activa manteniendo o pulsando la **barra espaciadora** (cuando el foco no esté dentro de un campo de texto) o haciendo clic en el botón de micrófono en pantalla (pensado para teléfonos y tabletas). No habrá escucha continua en segundo plano desde los navegadores.
  - **Salida de audio en el cliente:** la respuesta de voz sintetizada por Piper para Haku Inventario se enviará como audio al navegador web y se reproducirá **exclusivamente en los parlantes/auriculares del dispositivo cliente**. Jamás debe sonar en los altavoces físicos del servidor.

### 12.2 Identidad, sesión y confirmación

- Haku Inventario utiliza la sesión web activa de Django[cite: 1]. Si no hay sesión, solicita en pantalla ingresar usuario y contraseña por teclado (nunca hablados)[cite: 1].
- El contexto conversacional de Haku Inventario caduca tras **30 minutos de inactividad**, sin cerrar la sesión web recordada de 7 días[cite: 1].
- **Confirmación obligatoria en dos pasos:** toda orden de voz que cree o modifique datos genera primero una **propuesta pendiente de confirmación** y Haku resume verbalmente y en pantalla los datos exactos (operación, producto, cantidad, almacén/ubicación y destinatario)[cite: 1]. Solo cuando el usuario confirma ("Sí, confirmar"), el backend vuelve a validar sesión, permisos y stock disponible y ejecuta la transacción[cite: 1].

### 12.3 Concurrencia del modelo (GPU)

Como el modelo Llama 3.1 8B en Haku serializa el acceso mediante un bloqueo (lock)[cite: 1], el adaptador debe encolar de forma segura las peticiones de Haku Visitante y Haku Inventario sin lanzar inferencias paralelas sobre el mismo objeto no reentrante[cite: 1]. Las consultas directas en la interfaz web nunca pasan por el LLM. Si el servicio de Haku está apagado o falla, toda la aplicación web de inventario sigue operando con normalidad[cite: 1].

## 13. Seguridad y Copias de Seguridad

- Validación estricta de permisos por almacén en el backend en cada vista y endpoint de API[cite: 1].
- Protección CSRF, cookies `HttpOnly` y `Secure` (bajo HTTPS local), y secretos en `.env` fuera de Git[cite: 1].
- **Política de respaldos:** copia automática incremental o dump ligero cada **2 horas como máximo**, copia completa diaria en carpeta local de respaldos, script listo para exportar copia a unidad USB externa, y restauración ejecutable únicamente por el Superusuario[cite: 1].
